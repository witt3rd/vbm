# Mark what is trusted, and derive what must be marked

What cannot be proven is marked as trusted. A repository keeps one `docs/trust-ledger.md` that names everything it relies on without proof (the compiler, the runtime, a C file, an FFI symbol, a vendored library, a tool), each entry with an owner and a plan (verify, replace, sandbox, or accept with a stated reason). A claim not yet proved sits in `docs/obligations.md` as `open` or `partial`, never silently. Every formally verified repository has a ledger: even a pure-Lean library trusts the Lean kernel, compiler and runtime. A repository that proves nothing and generates no code (the landing tool itself, the hub) has no claims to qualify and keeps none: a ledger marks the limits of a proof, and without a proof it has no meaning.
Completeness is DERIVED from the tree, never read from the ledger, so a definition cannot be relabelled out of it: the build pins, the toolchain pieces, every extern symbol, every trusted file, every vendored library (and the headers and externs it carries) and every tool the scripts run must each be named by an entry. The landing tool ships the check (`land-lean trust`); the repository's `.land/lean.conf` says where to look.
A vendored library is a ledger line (`pin:NAME`), and a repository claims no better than its dependency does. Count the base on every change: the number of entries and of entries with no written contract or no test.
The kernel entry should say what a replay does and does not cover: `land-lean recheck` runs Lean's own checker in a fresh process, which narrows the trust (a declaration that bypassed the kernel is caught) without removing it (a kernel bug is shared).
This builds on `trusted-base-is-a-budget.md`; the entry format and the derivation are in vbm-land `docs/lean-gates.md`.
