# Decisions (the owner's; all accepted as recommended; 10 and 11 recommended and awaiting the owner; 12, 14 and 16 the owner's; 13 is the one OPEN QUESTION; 17 is main's, 18 the owner's; 19 main's; 15 recommended and awaiting)

1. **Floors and targets.** Verified: specified share 100% for a library (a runtime-kind subject carries its own documented baseline, which only rises), 0 unproved escapes, non-vacuity 100%. Bare metal: freestanding build passes, 0 libc symbols for libraries. Efficiency: within 2x of the best SCALAR comparator on throughput (floor 50% of its MB/s); the gap to a non-scalar (SIMD) comparator is stated on the card and never floored. REFINED by main (reversible; owner to confirm): within 20% of the best comparator is unreachable against a SIMD parser (simdjson, about 1,500 MB/s on the card corpus). Velocity: fast gate under 60 s, 0 open PRs. Honesty: every gate has a self-test and the attack suite passes.
2. **Comparator set.** For vbm-json: a public conformance corpus (JSONTestSuite) and peer implementations (simdjson, serde_json, Python `json`). A subject with no peer is compared to its own history only. `yyjson` only if the owner asks. Each comparator is marked `scalar = true|false` in the adapter's `[bench] comparators`; the floor is against the best scalar one. Comparators are built OUTSIDE the sandbox (network at build time only, `scorecard/comparators/build.sh`), mounted read-only with their pinned versions and sha256 hashes recorded on the card, and every number comes from one corpus named by its sha256.
3. **Scheduled host.** The time series runs on one Linux worker host, pinned (no other load) so throughput numbers are comparable; never a maintainer workstation.
4. **Adapter file shape.** One file `scorecard.toml` in the subject repo is the submission contract: declared source globs, proof commands and patterns, trusted-native file list, ledger path, test paths, fast-gate and bench commands; the scorecard rejects a missing or unknown key. Alternative rejected: a script printing JSON (it would be executable subject code).
5. **Definition of unit-test free.** A "hand-written test" is any executable case or expected-output file not produced by a generator from the spec at the pinned commit; generated vectors and a vendored public corpus are boundary evidence, not tests. Target 0; the card also reports the mutation score as the substitute. REFINED by the owner's delegate (reversible; owner to confirm): the count is TESTS OF THE SUBJECT'S CODE only (e.g. vbm-json's `tests/abi_test.c`, hand-written C test cases of the library: target 0, to be replaced by generated vectors run through the ABI). SELF-TESTS OF THE GATES AND PROCESS SCRIPTS (the declared `[tests] gate_selftests`, under `scripts/`: `test_githook`, `test_land_direct`, `test_protected_set`, `test_run_parallel`, and `test_abi.sh` as a runner) are REQUIRED by process honesty ("a gate you have not watched fail is decoration"), so they are counted under PROCESS HONESTY as a presence-and-coverage metric (`honesty.gate_selftests`) and are not penalised under by-construction. Limit: the adapter declares them, so the card lists the files and a self-test glob outside `scripts/` is rejected. The first card (6 files) mixed the two and is superseded. REFINED AGAIN (owner via main; reversible): the metric counts CASE LITERALS, not files. A test file's cases are the calls to the adapter's `entry_points` with a string or bytes literal in their arguments (its own input and expected values), plus one for each declared `scenario_files` entry (inputs built in code); a DRIVER that only loads GENERATED vectors and compares verdicts has 0 cases and is listed as a driver, not counted. With no `entry_points` declared every candidate file counts as one case, so declaring nothing never helps. Limit: the adapter names the entry points; the card lists cases and drivers per file so a reviewer can check the classification.
6. **Not-measurable policy.** It fails the floor unless a named substitute is reported (as written in SPEC). Alternative: it only warns.
7. **Runtime-kind subjects vs libraries.** One card with the same seven ideals, but a subject of kind `runtime` (handler code is named, not proved) may carry a documented lower floor on "verified" with a dated plan to raise it; the floor is its current baseline and may only rise. Its adapter and card live in its own repo, not here.
8. **Mutation and fuzz budgets.** Scheduled only (not in the fast gate), N = 1M fuzz inputs, fixed seed, plus 200 spec mutants.
9. **Project name and visibility.** Private until the owner says publish; built public-ready. The name is `vbm`, set in `project.toml`; the lint flags the retired name.
10. **Sandbox technology (RECOMMENDED, awaiting the owner).** Executing metrics run only in a rootless-podman container (docker as a fallback) on the dedicated worker host: no network, read-only subject mount, tmpfs scratch, CPU/memory/pids/disk/time limits, dropped capabilities, default seccomp, a pinned image by digest, the attestation recorded in the card. Alternative: bubblewrap with `--unshare-net` and the same mounts (lighter, no image, weaker attestation, no disk quota). SUPERSEDED by 12 and 13 for Level 2 (a microVM per job replaces the container; no podman launcher will be built); bubblewrap remains the launcher of the Level 1 checker and of the interim Level 2 on our own repos. The bubblewrap launcher `scorecard/sandbox-bwrap` is built and passes `scripts/sandbox-conformance.sh` (the dev and CI launcher; memory, process and CPU limits are a cgroup scope where the user manager exists, else rlimits, and the attestation says which; toolchains are bound read-only, and their PATH and variables set, from a local `sandbox-bwrap.binds`); the podman launcher is not built yet. Without a launcher the runner executes nothing of a subject.
11. **One repository; registry flow (RECOMMENDED, awaiting the owner).** Guidelines, scorecard and registry live in one repo. A registry entry `registry/<owner>__<repo>.toml` is added by a pull request (the only place PRs exist here, for external contributors); the repo's own CI validates the entry, scores it in the sandbox on the worker host and commits the score to main; a contributor can never write a score. Details: SPEC, "Registry and contribution flow".
12. **Two levels (the owner's: yes).** The scorecard and the registry have TWO LEVELS. Level 1, Certified, is the default, runs NO candidate code, and works from a proof export plus a manifest rechecked by an independent kernel (nanoda) in the minimal sandbox, with static checks of declared files. Level 2, Measured, runs the candidate's artifact; it is expensive, so it is by SPECIAL CONSIDERATION only: requested in the registry entry with a reason, approved by a maintainer, capped per month. The card shows the level and a verdict per level (`Certified`, `Certified + Measured`). Every number is scorer-computed or labelled `self-reported` and never counts toward a pass line. vbm-json is the first Level 2 subject; until the isolation exists it runs on our worker host in a resource-limited process, and its card says so. SPEC: "The two levels".
13. **OPEN QUESTION for the owner: the Level 2 HOST.** Level 2 needs a machine that is credential-free, off the private network, running a fresh microVM per job (own kernel, ephemeral disk, no network, destroyed after). Options: (a) a spare physical box kept credential-free and off the private network; (b) a throwaway cloud VM in an EMPTY, capped account, created per batch and destroyed; (c) none yet (Level 2 stays on our worker host for our own repos only). RECOMMENDATION: **a credential-free ephemeral microVM host** (the design above, whichever of (a) or (b) carries it); of the two, (b) in an empty capped account needs no hardware on the private network and its worst case is a bill the cap bounds, (a) is cheaper per job but has to be kept clean by hand. Nothing of the host is built until the owner picks.
14. **Allowlist until the isolation exists (the owner's).** The registry accepts only repos on `registry/allowlist.toml` (ours) until the Level 2 isolation is built; an outside submission is refused with a message naming the isolation requirement. The allowlist is gate-defining (protected path); the validator and the runner both enforce it; a registry entry for a non-allowlisted repo fails validation, and an allowlist edit is reported by the protected-set gate. SPEC: rule 10 and "Registry and contribution flow".
15. **Level 1 definitions (RECOMMENDED, awaiting the owner; reversible).** (a) A Level 1 dimension passes on its Level 1 floored metrics only; efficiency is Level 2 only; the verdict `Certified` needs every Level 1 floor to pass and `not-measurable` fails. (b) "Standard axioms" are exactly `propext`, `Classical.choice`, `Quot.sound`; `Lean.ofReduceBool` (native_decide) is NOT standard. (c) Non-vacuity at Level 1 is the syntactic checks listed in the SPEC, reported as sampled evidence; the mutation form is Level 2. (d) The export is limited to 64 MiB and 1,000,000 lines. (e) On hosted CI the real kernel is `not-measurable` and the sandbox negative self-tests use a stub checker; the real kernel runs on the registry's worker host.
16. **Tier 1 runs on GitHub-hosted runners only.** `.github/workflows/tier1.yml` runs on `ubuntu-latest`. A self-hosted runner must never take a stranger's pull request, so a public repo may not name one: `scripts/check-ci-visibility.py` runs in Tier 1 and FAILS when the repo is public and any workflow job is self-hosted (or the visibility cannot be read); its negative self-test is `scripts/test_ci_visibility.sh`. While a repository is private and ours-only a self-hosted runner is allowed; a repository that used one switches back to hosted runners before it is made public (`skills/flip-checklist`).
17. **Tier-1 time is two metrics: warm and cold (main's refinement of the velocity metric; reversible; judged by main as the independent judge of metric-definition edits).** The single `velocity.tier1_seconds` (floor under 60 s) measured a fresh clone with no cache: 494.5 s on the card of vbm-json v8, which is what an outside contributor pays and not what a landing costs. It is RETIRED and replaced by two metrics, both printed on the card and neither hidden or averaged into the other. `velocity.tier1_seconds_warm`: what a LANDING costs, floor under 60 s: the fast gate (delta mode) on a typical change, on the cache the cold run just left, timed by the runner. `velocity.tier1_seconds_cold`: what an OUTSIDE CONTRIBUTOR pays, a CEILING of at most 600 s: the fast gate in a fresh clone and sandbox with no cache (494.5 s passes the ceiling and is shown). A regression in warm time fails Landedness; a cold run past the ceiling fails it too. The relabel risks of a warm number the adapter itself declares (a warm command that runs nothing, a change class that selects nothing, a skip list that hides the gates, a forged clock) are closed in the SPEC row and the self-tests: the warm run must exit 0 and show the self-test evidence of every declared gate except named `warm_skips` (never all), phases are timed on the host clock by nonce-stamped lines the runner's own wrapper prints, and the declared change class is on the card for the judge to read. Cards written before the split read Landedness `pending`.
18. **The verdict is correctness first, landedness second (the owner's ruling).** "The important metric is actually CORRECTNESS, secondarily LANDEDNESS." The card's verdict is restructured, with no single blended score and no averaging: HEADLINE `Correctness: PASS|FAIL` from the primary ideals (Verified, By construction, Trusted generation, Process honesty), each with its floor; SECOND `Landedness: PASS|FAIL|PENDING` from velocity (tier-1 warm and cold, open PRs; red minutes and the revert/escape rate join when they have metrics); THEN the remaining ideals (Bare metal, Efficiency) as a profile, with values and floors, in neither of the two lines. The registry table shows two columns, Correctness and Landedness (`pass`, `fail`, `pending`, `unscored`), and the card link; the registry's `[latest]` carries `correctness` and `landedness` instead of `result`. One page still. MAIN'S ADDITIONS (approval of the attack list): the Correctness line states its coverage, `PASS (3 of 4 primary dimensions measured; Trusted generation not yet defined)`, never a bare PASS while a primary dimension is undefined; and the card page prints `skipped N of M gates` beside the warm number. The VBM manifesto says the same order. SPEC: "The verdicts"; `scorecard/scorecard_verdicts.py` is the one place the groups are defined.
19. **The honesty check: a gate whose self-test ran nothing fails Process honesty (main approved the evidence-format lane; reversible; judged by main as the independent judge of metric-definition edits).** A negative self-test that passes because the thing under test never ran (a refused heavy tool, a skip, an early exit) is decoration, and `honesty.gates_self_tested` cannot see it: its pattern matches a line the self-test prints on any path. New floored metric `honesty.selftests_ran_cases` (dimension honesty, so Correctness; floor at least 1 case): the fast-gate log must carry the ran-evidence the subjects emit (stdout line `^ran: [A-Za-z0-9_.-]+: [0-9]+ cases$`, N summed over lines and positive, no line with `SKIPPED`); zero cases, a SKIPPED line and no evidence EACH fail, and only Process honesty (self-tests plant each). The runner reads the log itself in its own code (the subject's `scripts/ran-evidence.sh` is never run), only through the sandbox, from the fast gate's own output; the adapter exposes the log by what its `[tier1] command` prints and MUST declare `[tier1] ran_names` (main's condition 1: the evidence names of its declared gates, none declared is not-measurable): the evidence names must equal that set, so a gate the subject invents, a declared gate that dropped its line and one that reports 0 each fail by name. The card page shows the coverage (cases, evidence lines, FAIL reason) and, with the metric, the honest weakness in main's words: "a count regex proves a count was printed, not that every case was meaningful". Existing cards v1 to v9 are not re-scored: they stay as written, and a card with no such metric says in its header "Scored before the honesty check (ran-evidence): Process honesty here does not include it" (card page and card.md; `scorecard_verdicts.pre_honesty`); the next run of a subject without evidence flips it to FAIL. Follow-up slice (main's condition 2, not in this landing): the same evidence check on the WARM log. Not done here, and the evidence producers, which land in each subject repo (vbm-json first).
