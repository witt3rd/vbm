# SPEC: the scorecard (two levels, the seven ideals, the sandbox)

**What it is.** A scorecard run measures a submitted repo against the seven ideals of VBM and writes ONE JSON per level. Every number is SCORER-COMPUTED from raw data (the tree, a proof export, a build, a run) or is labelled `self-reported` and never counts toward a pass line; a doc that says "about 20 s" is not a measurement.
There are TWO LEVELS (section "The two levels"): **Level 1, Certified** (the default; runs no code of the candidate) and **Level 2, Measured** (expensive; by special consideration only). The card shows the level and a verdict per level: `Certified` or `Certified + Measured`.
The standard is called VBM (verified bare metal); the method the guidelines describe is agentic: software that agents write, with no line-by-line human review. Libraries that follow it are named `vbm-<name>`.
The scorecard is public: a repo that claims the exemplar criteria is submitted, scored and listed with its score in a registry; the guidelines are published. Until the Level 2 isolation exists the registry accepts only allowlisted repos (ours; rule 10). vbm-json (a verified JSON codec written once in a proof assistant) is the v1 subject and the only named exemplar.
The rubric is toolchain-neutral: a metric is defined by what it counts, never by a language. Language-specific commands and patterns live only in the subject's adapter (`[proof]`, `[tier1]`, ...).

**Rules.**
1. **Pinned.** The card runs on one named commit of the subject and one named commit of the scorecard; both SHAs, the adapter hash and (when code ran) the sandbox attestation are in the JSON. Same commits, same bytes out, except the wall-clock values a metric measures (marked `measured: true` on the metric: they vary with load and are not part of the byte-identity claim; every other byte is identical).
2. **Floors, no averaging; two verdicts, then a profile (DECISIONS 18, the owner's ruling).** Each ideal has a FLOOR (a pass line on its metrics). One ideal below its floor fails ITS verdict, per section "The verdicts": there is no single blended score and no averaging across verdicts.
3. **Honest status.** Each metric is `pass`, `fail` or `not-measurable`. `not-measurable` counts as a FAIL for the floor unless a NAMED SUBSTITUTE metric is reported beside it (see "Cannot be fully measured").
4. **Time series.** Each run appends its JSON to a history; a scheduled run on a pinned worker host with no other load keeps it. The page shows trend, not only today.
5. **Any repo, one adapter.** The submission contract is one file, `scorecard.toml` (named commands and declared paths for each source below). The scorecard knows no repo by name.
6. **Own lander.** Lands only through its own `scripts/land-direct`: no PRs, main green at every commit.
7. **Self-protected.** The metric definitions, targets, floors and the adapter schema are protected paths; changing one is a gate-defining edit, judged by the attack suite (ideal 7), not by taste.
8. **Untrusted subject.** The submitted repo is untrusted code. Static metrics read only declared files; every metric that must execute subject code runs inside the sandbox (section below), and the runner refuses to execute it anywhere else.
9. **Two levels.** A metric belongs to exactly one level (the `L` column below). Level 1 executes nothing of the candidate. A Level 2 metric never makes a card `Certified`, and a missing Level 2 run never fails a Level 1 verdict.
10. **Allowlist until the isolation exists.** The registry accepts ONLY repos on `registry/allowlist.toml` (ours) until the Level 2 isolation of "Level 2 isolation (the required design)" is built. An outside submission is refused with a message naming that section. The allowlist is a gate-defining file (protected paths).

Columns: **L** = the level the metric belongs to (1 Certified, 2 Measured). **dir** = which way is better. **Comparator** = an independent thing measured the same way, so a number is never judged alone. **Today** = vbm-json at its pinned commit (`-` = not measured yet).

## The verdicts
The owner's ruling (DECISIONS 18): the important question is CORRECTNESS, the second is LANDEDNESS (how fast and cleanly changes land). A card therefore reads, in this order and on its first two lines: `Correctness: PASS|FAIL`, then `Landedness: PASS|FAIL|PENDING`; then a PROFILE of the remaining ideals, with their values and floors, in neither verdict. The groups are fixed in `scorecard/scorecard_verdicts.py` (one function, used by the runner, the page and the registry table):
| Group | Ideals | Verdict |
|---|---|---|
| Correctness | 1 Verified, 3 By construction, 4 Trusted generation (no metric is defined yet: the card lists it as `not_defined_yet`, never silently dropped), 7 Process honesty | `pass` when every floored metric of them passes (`not-measurable` fails its floor), else `fail` |
| Landedness | 6 Velocity: tier-1 warm and cold, open PRs; tracked: commits per hour, p90 commit-to-main. Red minutes on main and the revert/escape rate are listed in the table below and join the verdict when a metric implements them | `pass`, `fail`, or `pending` for a card scored before the warm/cold split (it carries the retired `velocity.tier1_seconds`: a definition that no longer exists cannot judge it; re-run the card) |
| Profile | 2 Bare metal, 5 Resource efficiency | none: each dimension's own `pass`/`fail` and its metrics are shown, and neither verdict line includes it |
The Correctness line states its coverage while a primary dimension is undefined and is never a bare PASS: `Correctness: PASS (3 of 4 primary dimensions measured; Trusted generation not yet defined)` (card, page, registry column and README table; `scorecard_verdicts.label`). On the card page the warm row prints `skipped N of M gates` beside the warm number (the table does not). A regression of a correctness metric flips Correctness and not Landedness; a regression of a landedness metric flips Landedness and not Correctness (`scripts/test_scorecard.sh` plants each). The registry table has the same two columns (`pass`, `fail`, `pending`, `unscored`) plus the card link. The card has no `result` and no `implemented_result`.

## The two levels
| | Level 1: CERTIFIED | Level 2: MEASURED |
|---|---|---|
| Who gets it | every registered repo (the default) | by special consideration only: it is expensive |
| Candidate code run | NONE, anywhere | yes, in a fresh microVM per job (the required design; see "Level 2 isolation") |
| What the candidate submits | a PROOF EXPORT made on their machine plus a MANIFEST (a data file: no commands) | an adapter (`scorecard.toml`: commands) and the pinned source |
| What the scorer does | rechecks the export with an independent kernel, reads statements, axioms and escapes from it, checks submitted artifacts and declared files statically | builds and runs the artifact: efficiency against comparators, differential and fuzz, mutation, reproducible build twice, an independent second compile |
| Verdict | `Certified` | `Certified + Measured` (Level 2 never replaces Level 1) |

**Number hygiene (both levels).** A value is `scorer-computed` (the scorer derived it from raw data: the export, a file, a git history, a measured run) or `self-reported` (read from a file the candidate wrote: a manifest field, a claimed size, a count in a doc). The card marks every value with its `source`. A `self-reported` value is shown, never judged: it has no floor, and cannot make a metric pass.

**The card.** `level` is the highest level that passed (`0`, `1` or `2`); `badge` is `Not certified`, `Certified` or `Certified + Measured`; `levels.1` and `levels.2` each carry their own `verdict` (`certified`/`not-certified`; `measured`/`not-measured`/`not-requested`), their metrics and their dimensions. The floors are per level: a Level 1 dimension passes when every Level 1 metric that has a floor in it passes (`not-measurable` fails, as always); a dimension with no Level 1 metric (efficiency) is a Level 2 dimension only. A Level 2 verdict is only ever produced for an entry that carries an approved Level 2 request.

## Level 1: Certified (no candidate code runs)
1. **Submit.** In the subject repo, a PROOF MANIFEST (`vbm-proof.toml`, named by the registry entry's `manifest`; unknown or missing keys rejected, no key holds a command) and the export it names. The manifest: `[export]` the path of the export (a Lean declaration export in the lean4export NDJSON format, produced on the candidate's machine; format 3.1.x, the range the independent kernel accepts), `lean_version` (self-reported); `[claims]` `theorems` (the theorems that CARRY THE CLAIM) and `definitions` (the definitions they are about); `[artifact]` the shipped artifact(s) (path, kind `wasm` or `object`, `allowed_symbols`); `[binding]` `generator` and `compiler`, ids of two entries of the trust ledger; `[trust]` the trusted native files, the ledger path and its entry regex; `[tests]` the test paths and entry points; `[source]` the declared source globs, `[proof] sorry_pattern`, `allow_marker`; `[velocity]` window. Paths are relative, without `..`, tracked at the pinned commit.
2. **Intake.** The export is read as DATA by the one file guard of "Untrusted subject code" (regular file, no symlink) with stricter caps: at most 64 MiB, at most 1,000,000 lines, at most 1 MiB per line, UTF-8 JSON objects only, the first line a `meta` object with format version 3.1.x, names, levels and expressions numbered densely and in order, every id defined before use, every object has exactly one known tag key, indices within the number of lines, an expression DAG depth cap (no recursion over an attacker's depth: the reader is iterative) and the reader runs under a wall-clock alarm and an address-space limit. Anything else is rejected: the metric is `fail` with the reason (an unreadable export is never `not-measurable`: the candidate chose its bytes).
3. **Recheck.** The independent kernel (nanoda; its binary pinned by version and sha256, recorded on the card) rechecks the export. The checker still PARSES UNTRUSTED DATA, so it runs ONLY in the minimal sandbox: no network, no secrets, the export mounted read-only, memory/CPU/disk/pid/time limits, nothing else visible; the target is a microVM (own kernel, ephemeral disk) and a memory-safe checker, and today the sandbox launcher is the bubblewrap launcher of "Untrusted subject code" with the same contract (the card's attestation names the launcher kind: `bwrap` is the weaker form, never a claim of a microVM). On hosted CI the checker is not installed: the real-kernel step is `not-measurable` there and its negative self-test runs a stub checker through the same launcher and contract; the real run is a Level 1 run of the registry's worker host. No sandbox configured: `not-measurable` ("sandbox not configured"), never executed on the host.
4. **Read.** From the export, by the scorer's own reader: which theorems exist and their statements (printed); the AXIOMS in the transitive closure of each claim theorem (constants reachable through types and values; only the three standard axioms allowed); escapes in that closure (unsafe/partial definitions, unsafe axioms, opaque constants); NON-VACUITY evidence where checkable (the table row above lists the exact checks; a failed check names the theorem); the definitions the claims are about, written out for human review in the card. Each check has a negative self-test (a planted `True` theorem, a `False` hypothesis, a `sorryAx` dependency, an unsafe definition, a missing claim).
5. **Static artifact checks** (a declared file read as data, never executed): symbol table of a submitted freestanding artifact (`.wasm`: the scorer's own import-section reader; an object or archive: `nm -u` in the sandbox, because `nm` parses untrusted data), sizes, trusted native line count and trust-ledger entry count of the declared files, test-case literals (the hand-written CASES count of "Correct by construction"), history metrics (commits per hour, p90 commit-to-main, open PRs: the forge API and git history).
6. **The binding is a named ledger entry.** What no Level 1 step proves is that the shipped artifact is the compiled form of the proved definitions. That gap is the generator and the compiler: the manifest names the trust-ledger entry for each, the card prints both entries by name next to the artifact's sha256, and the verdict needs both to exist. **Design note (not built):** the upgrade is for the scorer to regenerate the C from the CHECKED declarations itself and compare it with the shipped file, so the generator entry shrinks to the scorer's own; until then both entries stay on the card as trust.

## Level 2: Measured (by special consideration)
Level 2 runs the candidate's artifact, which is the expensive and the dangerous part, so it is OPT-IN, never automatic.
- **Request.** The registry entry carries a `[measured]` table with a `reason` (why this repo needs measured numbers; at least 40 characters) and the adapter path. It is only RUN once a maintainer approves it: `approved = "YYYY-MM-DD"` in that table, written by a maintainer's own landing, never by a contributor (the validator rejects a contributor change to `approved`). Approvals are CAPPED per calendar month (`measured_per_month` in `registry/allowlist.toml`); the validator fails an entry whose approval would exceed the cap.
- **What it runs** (all inside the isolation below): efficiency against comparators, differential agreement and fuzz, code and specification mutation, a reproducible build twice, the independent second compile, the fast-gate time and the subject's own attack suite: the Level 2 metrics of the tables above.
- **Interim (our own repos only).** Until the isolation exists, Level 2 runs on our worker host in a resource-limited process (bubblewrap with cgroup limits) and ONLY for allowlisted repos; the Level 2 card says so in its `isolation` field (`"resource-limited process (bubblewrap), not a microVM"`). vbm-json is the first Level 2 subject; its existing card is such a run.

## Level 2 isolation (the required design; not built)
No outside repo is accepted until all of this exists. (The host is the owner's open decision, DECISIONS 13.)
1. **A fresh microVM per job**: its own kernel, an ephemeral disk, destroyed after the job; nothing survives to the next job.
2. **A dedicated, credential-free machine that is not on the private network**: no secret, token, key or mount of ours exists on it; it can reach nothing of ours. Subject code never runs where secrets live.
3. **No network inside the VM** (not even loopback services of the host); the subject is fetched BEFORE the job as a pinned ARCHIVE of the commit (no hooks, no submodules, no LFS, size-capped, hash recorded) and handed in read-only.
4. **Hard caps**: CPU, memory, disk, process count and wall time, enforced by the VM and the host's supervisor, not by the guest.
5. **One narrow result channel**: the guest writes ONE results file; the host reads it with a size cap and validates it against a schema (hostile output: no path, no markup, no number outside its range is trusted) before it enters a card.
6. **The scorer owns the measurement**: wall time and resource use are measured by the host from OUTSIDE the VM; a number the guest prints about itself is `self-reported` and ignored. Comparators are built by us, hashed and mounted read-only.
7. **Hostile output**: anything the subject produces (stdout, file names, numbers) is data, capped and escaped; it is never interpreted, joined into a path or placed in a card unescaped.

## Untrusted subject code (the hard part)
A submitted repo is attacker-controlled: its build, tests, benches, adapter commands, file names, symlinks, regexes and output are all hostile until shown otherwise. Two classes of metric, two rules.

**Static metrics** (scans, counts, history) execute nothing of the subject. They read ONLY files the adapter declares (`[source] globs`, `[trust] c_files` and `ledger`, `[tests]` globs) and that are tracked at the pinned commit. Every read goes through one guard: the path is relative, has no `..`, is a regular file by `lstat` (a symlink is never followed, listed as skipped), and is at most 5 MB (larger: skipped, counted). A glob that is absolute or contains `..` is rejected with the adapter. Adapter-supplied regexes are hostile (catastrophic backtracking): every metric runs under a wall-clock alarm and a runaway is `not-measurable`. Git is run with a scrubbed environment (no global or system config, no hooks, no fsmonitor); the subject is only cloned into a scratch dir and the clone is deleted.

**Executing metrics** (build, closure gate, fast gate, tests, benches, fuzz, mutation) run ONLY inside a sandbox, via a launcher the runner is given (`--sandbox <launcher>`). With no launcher the runner executes nothing of the subject: those metrics are `not-measurable` ("sandbox not configured"). The launcher contract:
- **Isolation.** A container (rootless podman or docker) or bwrap with a network namespace: NO network (loopback only), a fresh PID/IPC/mount namespace, no host paths except the two mounts below, no credentials, no inherited environment (the runner passes a clean environment; the launcher passes none of the caller's), non-root, no new privileges, all capabilities dropped, default seccomp.
- **Mounts.** The subject checkout read-only at `/subject`; one scratch output dir read-write at `/out` (size-limited tmpfs); a private tmpfs `/tmp`. Nothing else, so an undeclared host file, `~`, the docker socket and the runner's own scratch are unreachable.
- **Limits.** CPUs, memory (OOM-killed), disk (tmpfs size), process count, wall time; defaults 2 CPUs, 4 GiB, 2 GiB, 512 pids, at most 3600 s per command (an adapter's timeout may only lower it). On time-out the whole process group/container is killed and the launcher exits 124. Output the runner keeps from a command is capped at 1 MB and only parsed with the adapter's regex.
- **Never on a maintainer workstation.** The runner refuses a launcher whose attestation is not from the dedicated worker host class; the registry's scores are produced on that pinned host only. Subject code never runs where secrets live.
- **Attestation.** For each command the launcher writes `/out/attestation.json`: `image_digest` (the sandbox image's content digest), `network` (`"none"`), `subject_mount` (`"ro"`), the `limits` applied, the launcher's own version. The runner rejects a missing or non-conforming attestation (metric `not-measurable`) and records every attestation, the launcher hash, the subject commit and the limits in the card, so a score is reproducible and its sandbox auditable.
- **Launchers.** `scorecard/sandbox-bwrap` (bubblewrap: user/pid/net/ipc/uts/cgroup namespaces, read-only `/usr` plus the toolchain directories listed in `sandbox-bwrap.binds`, `/subject` read-only, tmpfs `/tmp` and `/out`, `prlimit` limits; weaker than a container: no cgroup accounting, `image_digest` digests the exposed host userland) is built and conformant. The Level 2 target is a microVM per job ("Level 2 isolation"); no container launcher is planned (DECISIONS 10, 13).
- **Conformance.** `scripts/sandbox-conformance.sh <launcher>` probes a launcher: a TCP connect to a loopback listener must fail; a file outside the mounts must be unreadable; a planted environment variable must not appear; a write into the subject must fail; a runaway must be killed at its time limit; the attestation must parse. A launcher lands only if it passes; the conformance script is itself shown able to fail (Tier 1 runs it against a deliberately leaky launcher and requires it to fail).
- **Resource exhaustion.** Fork bombs, memory and disk fills, and endless output are bounded by the limits above; a limit hit is `fail` with the reason, never a hang of the runner. Symlink escape and path traversal: the subject is mounted read-only and never written; output is read back from `/out` only by fixed file names; no subject-supplied path is joined into a host path.

## Cannot be fully measured today (said plainly)
- **Unit-test free.** No tool proves a repo has no tests; a test can be hidden as a script, a golden file or a vector. The card reports what is countable: hand-written files by a fixed definition, plus the mutation score. Status is `not-measurable` for the claim itself; the floor is met only by the substitutes (zero hand-written files AND mutation score at target).
- **Trusted base of the proof assistant's kernel and the C compiler.** Both are in the base of every artifact and neither is proved. The card reports the ledger entries naming them, the pinned versions, the independent proof checkers' result and the independent second-compiler differential (ideal 4). A missing substitute fails the floor.
- **Level 1 binds proofs to definitions, not to the shipped bytes.** The export proves the named theorems about the named definitions; that the artifact is their compiled form rests on the named generator and compiler ledger entries until the scorer regenerates the artifact itself (the design note in Level 1). The syntactic non-vacuity checks catch trivial statements, not all vacuous ones.
- Non-vacuity and the fuzz differential are sampled, not exhaustive: reported with N and seed.

## Registry and contribution flow
The registry is `registry/`: one entry file per submitted repo, named `<owner>__<repo>.toml`, and ONE allowlist file `registry/allowlist.toml`. An entry (`scorecard/registry-validate` defines the schema; the common keys are required, the scoring keys only for a live entry, unknown keys rejected):
```
kind = "library|foundation|tool"                 # every entry; entries are listed before they are public
status = "live|coming soon|planned"              # live = public; only a live entry has the keys below, and without a card it is shown as unscored
                                                 # a live TOOL has `repo` only (listed and linked, never scored): commit, manifest, targets, [latest] and [measured] are refused on it; the kind never relaxes the rules for a library or foundation piece
what = "..."                                     # one line
milestone = "..."
depends_on = ["vbm-x"]                           # names of other entries
repo = "https://github.com/<owner>/<repo>"     # https GitHub URL; <owner>__<repo> must equal the filename; <owner>/<repo> must be on the allowlist
commit = "<40 hex>"                              # the pinned commit to score
targets = ["C"]                                  # the languages the repo claims to build for (claimed, shown in the table; not scored)
manifest = "vbm-proof.toml"                      # Level 1: a relative path in the subject repo, no ".."; the proof manifest ("Level 1")
[measured]                                       # OPTIONAL: a request for Level 2 (special consideration)
reason = "..."                                   # at least 40 characters: why this repo needs measured numbers
adapter = "scorecard.toml"                       # relative .toml path, no ".."; if the pinned commit has none, the maintainer-written scorecard/adapters/<repo>.toml (a stopgap)
approved = ""                                    # "" until a maintainer approves (YYYY-MM-DD); written ONLY by a maintainer's landing, counted against measured_per_month
[latest]                                         # written ONLY by the scoring job, never by a contributor
date = "YYYY-MM-DD"                              # empty until first scored
correctness = "pass|fail|unscored|pending"       # the Correctness verdict of the card (SPEC "The verdicts"); both unscored or both pending, else a scored entry has pass|fail here
landedness = "pass|fail|pending|unscored"        # the Landedness verdict; pending for a card scored before the warm/cold split; there is no single blended result
level = "none|certified|certified+measured|unscored"   # the badge: the highest level that passed
card = "registry/scores/<owner>__<repo>.json"    # the card (full JSON); empty until first scored
```
`registry/allowlist.toml`: `repos = ["<owner>/<repo>", ...]` and `measured_per_month = N`.
1. **Allowlist (until the isolation exists).** An entry whose `<owner>/<repo>` is not on the allowlist FAILS validation, with the message: "not allowlisted: outside submissions wait for the Level 2 isolation (scorecard/SPEC.md, 'Level 2 isolation (the required design)')". The runner applies the same rule to a repo whose origin is a GitHub URL. The allowlist is a protected path: an edit to it is a gate-defining change (the protected-set gate reports it; it waits for the owner). A contribution PR can never change it (rule 2).
2. **Contribute.** A pull request that adds or edits exactly ONE entry file, `[latest]` left unscored and `approved` empty (changing `commit` only forward). This is the one place PRs exist in this repo, for external contributors; everything else lands direct. While the allowlist holds only our repos, an outside PR is refused by rule 1.
3. **Validate (no subject code, runs on every PR).** The validator checks: the changed-file list is one `registry/<owner>__<repo>.toml` entry and nothing else (not the allowlist, no scripts, no workflows, no scores); filename pattern; key set and types; URL shape and host allow-list (GitHub); a full 40-hex SHA; no `..`/absolute manifest or adapter path; the allowlist; `[latest]` and `[measured] approved` unchanged from main; the monthly Level 2 cap; at most one open registry PR per owner; the repo is public and its size is under the cap (the forge API only).
4. **Score (the scoring job).** On merge, and on a schedule, the repo's own CI hands the entry to the worker host: clone the pinned commit and run Level 1 (`scorecard/scorecard certify`), then Level 2 only if the entry's request is approved (`scorecard/scorecard run`, SPEC "Untrusted subject code"). The CI job that scores holds no secret beyond a token able to push `registry/scores/` and the entry's `[latest]` block; subject code never sees it (a clean environment, a separate sandbox).
5. **Who commits the score.** Only the scoring job, as a bot commit directly to main touching only `registry/scores/<owner>__<repo>.json` and that entry's `[latest]`. A score is never self-reported or reviewed by taste: it is the scorer's JSON with the subject SHA, scorecard SHA, manifest/adapter hashes, export sha256, checker version and hash, and sandbox attestations in it.
6. **Abuse limits.** One scoring run per entry per day, a global queue depth cap, per-run limits from the sandbox, a size cap on the subject, a cap on registry entries per owner; an entry whose runs hit a limit three times is marked `fail` with the reason and not re-run until its `commit` moves. A removal request (owner of the repo) is a PR deleting the entry.
7. **Listing.** The table in `README.md` between its markers is generated by `scorecard/registry-table` from the entries and their cards (never hand-edited): name (linked when public), what it is, kind, status, Correctness and Landedness (`pass`, `fail`, `pending` or `unscored`: two columns, never one score) and the card link when scored. Tier 1 fails when the README drifts from the files (`scripts/test_readme.sh`), and when an entry's verdicts (derived from the card's dimensions) or commit disagree with its card.
