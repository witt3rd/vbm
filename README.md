# VBM: verified bare metal

VBM is a standard for software that is specified and proved in Lean, builds freestanding with no operating-system runtime, and is written by coding agents. Its components are named `vbm-<name>`, and each is scored by a program that recomputes every number from the repository. Correctness is the important measure and landedness (how fast and cleanly changes land) is the second; they are reported separately and never blended into one score.

[**Read the manifesto**](MANIFESTO.md): what the standard is, what it claims and what it does not.

**Status: early.** This repository is the standard and its tooling: the [guidelines](guidelines/INDEX.md), the scorecard program, and the registry of scored repositories. One library, [vbm-json](https://github.com/witt3rd/vbm-json), is scored so far, and its card says what it found: Correctness **fails** (three of the four ideals are measured; the check that its gates really ran is not yet measured for this subject, because its adapter does not declare the evidence lines to look for) and Landedness **fails** (the cold fast gate took 626 s against a 600 s ceiling, on a loaded shared host). The other registry rows are plans, not releases. Nothing here is a finished product, and the scorecard says what it cannot measure instead of guessing.

## Build and check

Everything runs through `mise` (it pins the Python of the runner, which is stdlib-only). You need `git`, `jq`, `bash` and `python3`; the sandboxed metrics also need `bwrap` (bubblewrap). The gate that every change passes, the same one CI runs:

```
mise exec -- scripts/tier1.sh
```

To score a repository: `mise exec -- scorecard/scorecard run --repo <path> --commit <sha>` (see [run-the-scorecard](skills/run-the-scorecard/SKILL.md)). Without `--sandbox` nothing of the subject executes.

## The seven ideals and their pass lines

A repo passes an ideal when every measured part of it is at or above its floor. A card has two verdicts, **Correctness** first (ideals 1, 3, 4 and 7) and **Landedness** second (ideal 6), then a profile of the rest (ideals 2 and 5) that is in neither; there is no single score and no averaging. One failed ideal fails its verdict, a metric the scorecard cannot measure counts as a fail, and the Correctness line says how many of its four ideals were measured (never a bare PASS while one, trusted code generation, has no metric yet).

1. **Verified.** The code that runs is the specification or derived from it: specified share 100% (a library), no unproved escapes and no non-standard axioms, non-vacuity 100% (a changed specification breaks a proof).
2. **Bare metal.** It builds freestanding and needs no libc symbols (or a short named list).
3. **Correct by construction.** No hand-written tests of the code (the tests are generated from the specification), mutation score 100%.
4. **Trusted code generation.** Reproducible builds, each artifact traces to its specification, generator and toolchain, and a second compiler agrees.
5. **Resource efficiency.** Within 2x of the best scalar independent implementation on throughput (the gap to SIMD parsers is stated on the card, not floored), with memory and latency tracked.
6. **Velocity (landedness).** The fast gate on a typical change, with its cache warm, runs under 60 seconds; a cold clone with no cache runs within 600 seconds; there are no open pull requests.
7. **Process honesty.** Every gate has a self-test that has been watched to fail, and the attack suite passes.

The exact definitions, floors and the reasoning are in [scorecard/SPEC.md](scorecard/SPEC.md) and [scorecard/DECISIONS.md](scorecard/DECISIONS.md).

## How to get listed

The registry lists the repositories we have scored. Anyone may run the scorecard on their own repository and publish the card ([run-the-scorecard](skills/run-the-scorecard/SKILL.md)): Level 1 certifies from a proof export, and nothing of your repository runs.

To be listed, open an issue here with the card. Listing without our review waits for the isolation that makes Level 2 (running subject code) safe ([register-in-the-registry](skills/register-in-the-registry/SKILL.md)).

## How scores are computed

A script reads your repo at the pinned commit and prints one JSON card: every number comes from a command, never from what a document says. Your repo is treated as untrusted code: files are read only if the adapter declares them, and anything that has to run (a build, a proof check, a gate) runs in a sandbox with no network, a read-only copy of your repo, no secrets and hard limits on time, memory and disk.
The card records the commit, the sandbox and its limits, so a score can be reproduced and audited. The design is in [scorecard/SPEC.md](scorecard/SPEC.md); the sandbox contract is checked by `scripts/sandbox-conformance.sh`.
